# 分层防御与 Phase 4.5

同类 bug 反复出现时必读。

## Phase 4.5：有进展的死循环

标准预算只抓两种情况：轮数超了、连续无进展。它抓不到第三种，而第三种最贵：

> 每一轮修复**都有进展**，但每一轮都翻出新的共享状态、隐式耦合或全局副作用。

这不是运气不好，是架构在说话。继续修下去每次都会"差一点就好了"，直到预算耗尽。

**触发条件**（满足两条即触发）：

- 连续 2 轮以上修复都产出了新发现（有进展，所以不触发无进展上限）。
- 每轮的新发现都指向不同位置的同一类问题——共享的可变状态、跨层的隐式约定、需要"记得同时改另一处"的耦合。

**触发后的动作**：停止修复，向 TeamLead 升级，议题是**架构**而不是当前这个 bug。修复方案要么改结构，要么明确接受现状并记录为已知限制——不能继续逐个打补丁。

`autopilot` 模式下 Phase 4.5 属于永远门禁：就地降级为门禁模式等人，不自行决定重构。

## 修在哪一层

同一个 bug 通常可以在多个层次上修。选择标准是**这一层能否让同类问题不可能再发生**。

```
用户看到 500
  ← 可以在这里 catch 住返回友好错误（症状层）
API 收到 null 用户
  ← 可以在这里加判空（下游层）
查询返回空结果但代码假设非空
  ← 可以在这里改成显式处理 Optional（接口层）
schema 允许该字段为空，业务不允许
  ← 可以在这里加约束（根因层）
```

优先修根因层。但注意：**分层防御不是在每一层都加判断**。每层都加判断会让错误被吞掉三次，最后没人知道真实原因在哪。

原则：

- **根因层修一次**，让错误不可能产生。
- **边界层报错**，让错误产生时能被立刻发现并定位（fail fast，带上下文）。
- **中间层什么都不做**，不吞异常、不填默认值、不做"防御性"判空。

中间层的判空是最常见的技术债形态：它让 bug 在离原因很远的地方以另一种形态出现。

## 反复出现说明什么

同类 bug 第二次出现时，不要只修第二个实例。问三个问题：

1. **有没有第三个实例？** 搜同样的模式，一次性全找出来。
2. **为什么这个模式容易写错？** 是 API 设计诱导的，还是缺少约束？
3. **能不能让它写不出来？** 类型约束、lint 规则、把危险操作收进单一入口、删掉那个容易误用的 API。

第 3 点做不到才退回"写进文档提醒"。文档提醒是最弱的防御，它依赖每个人每次都记得。

## 与预算的关系

Phase 4.5 触发时，「已用轮数」不重置。升级记录写进账本「问题闭环记录」，分类取 `process`（不是 `bug`）——因为要解决的是结构问题，不是那个现象。
