# 条件等待

涉及超时、竞态、异步等待时必读。

## 铁律

不用 `sleep` 等状态就绪。等条件，不等时间。

## 为什么 sleep 一定会背叛你

`sleep(2)` 表达的是「我猜两秒够了」。它同时制造两个问题：

- 机器慢一点（CI、负载高、冷启动）就不够 → 偶发失败，且难复现。
- 机器快的时候白等 → 套件越跑越慢，最后没人愿意跑全量。

偶发失败的代价不只是重跑一次。它会训练团队养成「红了就重试」的习惯，之后真实的 bug 也会被当成偶发。

## 正确形态

轮询条件 + 超时上限：

```python
def wait_until(predicate, timeout=5.0, interval=0.05):
    deadline = time.monotonic() + timeout
    while time.monotonic() < deadline:
        if predicate():
            return
        time.sleep(interval)
    raise TimeoutError(f"condition not met in {timeout}s")

# 用法
wait_until(lambda: server.is_listening())
wait_until(lambda: job.status == "done")
```

要点：

- 用 `monotonic`，不用 `time.time()`（后者会被系统时钟调整影响）。
- 超时必须抛错，不能静默返回——静默返回会把等待失败伪装成断言失败，误导下一轮诊断。
- 错误信息要说明等的是什么条件。

## 优先级顺序

能拿到事件就不要轮询：

1. **事件 / 回调 / future**：最准，零浪费。
2. **阻塞式 API**：`process.wait()`、`queue.get(timeout=...)`、`socket.connect` 带超时。
3. **轮询条件**：上面的 `wait_until`。
4. **固定 sleep**：只在一种情况下可接受——被等待方**没有任何可观测状态**，且你已确认无法引入一个。这时必须写注释说明为什么。

## 常见可观测条件

| 等什么 | 观测什么，而不是 sleep |
|---|---|
| 服务起来 | 端口可连接 / 健康检查返回 200 |
| 文件写完 | 文件存在**且**大小稳定两次采样，或写入方产出完成标记 |
| 异步任务完成 | 任务状态字段 / 完成回调 / 队列长度归零 |
| UI 更新 | 目标元素出现且可见，不是"等动画 300ms" |
| 日志出现 | 跟随输出流直到匹配正则 |

注意「文件存在」不等于「文件写完」——这是最常见的伪条件。

## 诊断竞态时

现象随机出现、加日志就不出现（海森堡 bug）→ 加日志改变了时序，说明就是竞态。

不要靠加日志定位。改用：

- 在可疑处主动放大时序差（临时插入延迟），看现象是否变成稳定出现。**能让它稳定失败，就已经定位了一半。**
- 检查共享可变状态：谁在没有锁的情况下读写它。
- 检查"检查后使用"（check-then-act）模式：检查和使用之间有没有让出执行权。

定位完成的标志是：你能主动构造出 100% 失败的时序，也能说明为什么修改后这个时序不再可能。
