# 根因追溯

进入诊断阶段必读。

## 铁律

没有验证过的根因，不改代码。

"我觉得大概是这里"不是根因。根因是一条你能主动触发、也能主动消除的因果链。

## 四个阶段与出口条件

阶段名本身没有约束力，出口条件才有。没达到出口条件不许进下一阶段。

| 阶段 | 做什么 | 出口条件 |
|---|---|---|
| 1 复现 | 拿到确定性的复现步骤 | 能连续跑两次都失败，且失败信息一致。间歇性失败必须先找到让它稳定失败的条件 |
| 2 定位 | 缩小到具体代码位置 | 能指出「删掉/改掉这一处，现象就会变」的具体行 |
| 3 解释 | 说清因果链 | 能回答「为什么这行会导致这个现象」，且链条上每一步都有观测证据，不含"应该"「可能」 |
| 4 修复 | 改最小的那一处 | 复现步骤不再触发，且原有测试全绿 |

跳过阶段 1 直接看代码猜，是最常见也最贵的错误。

## 单一假设原则

每次只提出**一个**可证伪的假设，写下来，再设计能推翻它的最小实验。

写法对照：

```
# 不可证伪：无法设计实验
"缓存有问题"

# 可证伪：能设计实验，也能被推翻
"getUser 在 key 未命中时返回了上一次的结果，
 因为 cache.get 的默认值参数在函数定义时求值了一次"
```

一次改五处然后现象消失了，你不知道是哪处起的作用，下次同类 bug 还会再来一遍。

## 最小实验

实验的目标是**推翻假设**，不是确认它。

- 只改一个变量。
- 预先写下「如果假设成立会看到什么」和「如果不成立会看到什么」。
- 跑完把实际输出记进诊断文档，不只写结论。

如果实验结果两种解释都能容纳，那这个实验不是最小实验，重新设计。

## 向上追溯，不在下游打补丁

现象出现的位置通常不是原因所在的位置。

```
现象：渲染时 user.name 是 undefined
  ↓ 往上问：谁给的 user？
  ↓ API 层返回的对象里没有 name
  ↓ 往上问：为什么没有？
  ↓ 查询语句 select 列表漏了 name
  ↑ 根因在这里
```

在渲染层加 `user.name ?? ''` 能让现象消失，但下一个用到 `name` 的地方还会再炸一次。**现象消失不等于根因解决。**

判断标准：如果你的修复是在数据流的更下游加判断、加默认值、加 try/catch，先回头确认上游为什么给出了不该给的东西。

## 二分定位

面对大范围不确定时，用二分而不是逐行读：

- 时间维度：`git bisect` 找引入变更。
- 代码维度：注释掉一半，看现象是否还在。
- 数据维度：砍一半输入，看现象是否还在。

每次二分都把结论写下来，避免绕回已排除的区域。

## 测试污染

某个测试单独跑通过、在套件里跑失败 → 是测试间的状态污染，不是这个测试的 bug。

定位方法：二分套件顺序，找出「加上它就失败」的那个前置测试。根因通常是共享的全局状态、未清理的临时文件、未重置的时钟或随机种子、未关闭的连接。

修在污染源，不要给受害测试加重试或加 `sleep`。
