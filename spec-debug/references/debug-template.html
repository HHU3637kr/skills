debug 文档模板

类型 template 角色 spec-debugger 骨架 A debugger/debug-001.html 骨架 B debugger/debug-001-fix.html 契约 html-report skill
用法

下面两个代码块各是一份完整可直接另存的 HTML 文档：整块复制（含 <!DOCTYPE> 到 </html>） 另存为 debugger/debug-001.html 或 debugger/debug-001-fix.html，再逐个替换 {占位符}。 样式路径 ../../../../html-report/assets/ 按 debugger/ 回到项目根的 4 层计算，项目实际层级不同需相应调整。

不允许功能退化

骨架里的 <meta name="rk:*"> 与 <link rel="rk-*"> 是原 YAML frontmatter 的机器可读等价物， .rk-meta 是同字段的人可读镜像，两轨缺一不可。关联产物分「本报告引用」（rk-links）与 「引用本报告」（rk-backlinks）两向，等价 Obsidian 双链的正向跳转 + 反向可发现。禁止删字段，禁止只写单向链接。

元信息字段说明

每个字段都有机器可读（<meta> / <link>）与人可读（.rk-meta / 关联产物列表）两轨，缺一不可。 原模板有几个 frontmatter 字段，HTML 就要有几个对应 <meta> / <link>，禁止因为「HTML 里看不见」就删字段。

标题必填必填rk:title / <title>h1问题诊断-简述 / 修复总结-简述
类型必填必填rk:type类型debug / debug-fix
Spec 目录必填必填rk:spec-dirSpec含分类目录

状态必填必填rk:status状态未确认 / 已确认 / 已归档

状态变更规则

触发条件状态变更
创建诊断或修复总结→ 未确认
TeamLead 转达用户确认诊断未确认 → 已确认
用户要求调整已确认 → 未确认
归档完成已确认 → 已归档

改状态时 <meta name="rk:status"> 与 .rk-meta 状态两处同步，缺一即失真。

撰写要点

  • 诊断：rk-cal risk 标问题现象，rk-cal key 标根因与设计关联，rk-cal warn 标风险评估；结论块用 is-fail（问题尚未解决）。
  • 修复：rk-cal ok 标已自检通过，rk-cal warn 标待 spec-tester 复验，rk-cal key 标为什么这样改；结论块先用中性，复验通过后改 is-pass。
  • 所有代码位置一律 <span class="rk-ref">file:line</span>。
  • 双向关联：本报告 rk-links 加一条时，对侧报告 rk-backlinks 补一条；对侧尚未产出先标注「（待创建）」，等产出后补齐。
  • 修改已确认文档时永不静默改写：修订号 +1（同步 rk:revision 与 rk:updated）、修订历史表追加一行、正文用 <del class="rk-del" data-rev="N"> / <ins class="rk-ins" data-rev="N"> 标记行内改动， <p class="rk-removed|rk-added" data-rev="N"> 标记整段增删。详见 html-report skill。
  • 修订历史保持 5 列不变。源于实质取舍的修订，「原因」列引用账本 Decision Log 编号（如 按 D-004（改走最小补丁））； 纯笔误、措辞、补充说明直接写清原因，不编造决策编号；决策过程正文留在账本，不复制进报告。
  • 禁止 <style>、行内 style=、外部 CDN；编号递增时同步替换文件名与全部链接（debug-002.html / debug-002-fix.html）。
