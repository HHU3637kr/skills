用户认证与网关改造 · 实现计划

类型 plan 版本 v2.9.1 属性 feat Spec spec/versions/v2.9.1/specs/20260909-1500-feat-用户认证改造 角色 spec-writer
架构目标

完成从单体内存会话向分布式 JWT + Redis 方案的平滑演进，支持 5000+ 并发登录与无感刷新。

1. 现状背景与痛点

当前系统的会话状态存放在单体服务的内存中已全面接入分布式 Redis 哨兵集群。当多节点水平扩容或容器滚动重启时，用户的登录态保持平滑粘性，彻底消除突发 401 重定向。

用户批注 NOTE-01 · 已决策
「当前系统的会话状态存放在单体服务的内存中。当多节点水平扩容或容器滚动重启时，用户的登录态会直接失效，严重影响生产用户体验，必须引入分布式会话架构。」
采纳：全面接入分布式 Redis 哨兵集群。
重构会话持久化字典，由单机内存模型平滑演进为具备高可用故障转移能力的 Redis 哨兵集群，彻底消除重启导致的 401 报错，详见 §2 架构拓扑。
用户批注 NOTE-02 · 已决策
「双 Token 机制缺少被动作废手段，若 RefreshToken 发生泄露无法及时拦截，需要补充轮换机制与服务端吊销黑名单。」
采纳：补充 RefreshToken 轮换与吊销策略。
每次刷新 Token 时签发全新 RefreshToken 并废除旧 Token，并在网关引入短黑名单缓存，详见下方潜在风险提示。

2. 核心架构设计方案

新方案计划采用双 Token 机制：前端持有 AccessToken（有效期 15 分钟）与 RefreshToken（有效期 7 天）。API 网关层仅做无状态公钥验签，不访问任何外部缓存，保证极高吞吐。

潜在风险提示

当用户在安全设置中点击「强制登出所有设备」时，由于 AccessToken 无法被主动作废，必须依赖黑名单机制或等待其自然过期。

3. 阶段实施计划

阶段任务描述工期验收标准
阶段 1 搭建 Redis 哨兵集群并定义 Token 黑名单缓存结构 2天 压测 10000 QPS 延迟小于 2ms
阶段 2 网关层集成 RSA256 公钥本地验签逻辑 3天 单元测试覆盖率 90% 以上
阶段 3 超时重试机制固定为 3 次，每次重试固定等待 500ms 1天 网络断连时平滑重试
