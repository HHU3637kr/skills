# Spec 工作流规范

## 基本约定

- 本项目采用 R&K Flow / Spec 驱动式开发，遵循「项目 → Version → Spec」三级架构
- 每个 Spec 必须归属明确的 Version，物理路径位于 `spec/versions/<version>/specs/<spec-dir>/`
- 新功能使用 `/spec-start`，需指定所属版本与需求性质（`feat` / `tech` / `debt` / `fix`，四类平权）
- 已有功能小迭代使用 `/spec-update`；要求全程 spawn 子 Agent 执行时用 `/spec-swarm` 启动（它只设执行形态，流程仍委派 `spec-start`）
- 实现前必须有**已确认**的 `writer/plan.html`（「已确认」的两种含义见下）
- 严格遵循 Spec，不添加计划外功能
- 收尾时使用 `exp-reflect` 沉淀经验到项目级 `spec/context/`，由 `spec-end` 执行**原位归档**（修改状态并保留在所在版本目录，禁止移出）并审查规范维护
- 角色（Who）与 Skill（How）严格分离

## 运行模式与执行形态

每个 Spec 在阶段一确定两个**正交**字段，一并写入账本 frontmatter。

### 运行模式 `mode`（谁验证）

写入账本 `mode` 与各报告 `rk:mode`。

- **门禁模式 `gated`**（默认）：每个关键节点等待用户确认。
- **自动驾驶模式 `autopilot`**：Agent 自主推进，但每个自主决策必须落账本且带可追依据。

**「已确认」有且只有两种含义**：

1. **用户确认** —— 用户明确表态放行。
2. **自门禁通过** —— 仅在 `autopilot` 下成立，且必须附带该门禁指定的机械证据。

没有证据的自我放行不构成「已确认」。

**模式的本质是换验证器，不是放宽标准。** 门禁模式下人是验证器；自动驾驶把人拿掉，就必须由指定的机械纪律补位。找不到补位物的门禁，一律列入「永远门禁」。

### 执行形态 `execution`（谁执行）

只写账本 `execution`，不进报告 meta——它是运行形态，不是报告属性。

- **串行 `serial`**（默认）：当前 Agent 按七角色协议依次承担职责。
- **编排 `swarm`**：当前 Agent 只做编排，角色产物一律由 spawn 的子 Agent 产出。

`execution` 与 `mode` 自由组合，四种全部合法。`swarm` **不放宽任何标准**：三条 Iron Law 与永远门禁清单约束的是角色行为，与角色跑在主进程还是子进程无关。

`swarm` 下两条固定约束：账本与 `rk-manifest.js` 仍由主控独占维护（并发写会互相覆盖）；子 Agent 没有 `ask` 工具，一切用户确认节点由主控代问。

## 决策依据的形式

任何自主决策落账本时，「依据」列只接受三种形式：

1. 文件路径 + 行号
2. 命令 + 退出码 + 输出位置
3. 用户原话引用

「根据经验」「通常做法」「这样更专业」不是依据。理由可以被生成，依据必须可追。

## 永远门禁（自动驾驶也必须停下等人）

判据是可逆性与治理面，不是风险高低：

- 运行模式的选择本身（不能自动驾驶地决定进入自动驾驶）
- 修改 `AGENTS.md` 或 `.agents/rules/`（自我修改治理规则）——自动驾驶下只产出建议，不落笔
- 合并分支、force push、直接改动主分支
- 根因涉及权限、计费、数据迁移，或需要绕过测试
- 超出已确认 plan 的范围扩张

自动驾驶遇到上述情形时**就地降级为门禁模式并等待用户**，不是中止任务。

## 三条不可协商的纪律

1. **测试先行** —— 没有失败的测试，不写实现代码。
2. **根因优先** —— 没有验证过的根因，不改代码。
3. **新鲜验证** —— 声明完成前，必须在当前工作树上跑一次验证并观察输出。引用历史结论、"应该没问题"、"逻辑上正确"都不算。

**这三条不因用户授权而失效。** 「我担责」「我核对过了」「就这一次」「演示在即」都不是例外——它们是压力，不是授权。

**把违规登记进账本不等于合规。** 「依据」列的作用是让决策可追，不是给破例开票；一条写明依据的违规仍然是违规。

真要跳过，唯一路径是：先就地降级为门禁模式，向用户说明将失去哪项保障并取得明确同意，且此后任何产物中都不得出现「已验证」「测试通过」这类结论。测试先行的唯一技术例外是改动不产生可观察行为（纯格式化、纯注释）。

细则由各 Skill 的 `references/` 承载，由该 Skill 的运行契约按机械可判的条件路由。

## 收到审查意见时

适用于任何角色收到任何来源的审查意见（用户、reviewer、tester、其他角色）：

- **禁止表演式赞同**：不要先说「你说得对」再照做。先复述意见，再验证它是否成立，然后才决定怎么做。
- **部分理解即停**：只理解了意见的一部分，就不要开始改。问清楚再动。
- **反查必要性**：被要求新增的东西，确认它有当下的真实需求，不是为假想的未来铺路。
- **该顶回去就顶回去**：意见与已确认的 plan 冲突、或基于错误前提时，带证据说明，不要默默照做。

### 报告批注（用户写在 HTML 报告里的意见）

用户可以直接在报告 HTML 里写批注，两种形式：

- 块级：`<div class="rk-note">意见正文</div>`
- 行内：给任意元素加 `data-rk-note="意见正文"`

**任何角色在接手一份报告前，必须先全文搜索 `rk-note` 并把每条批注登记进账本「问题闭环记录」**（分类 `review`，状态 `pending`，描述写批注原文）。漏读批注等同于漏读用户指令。

处理完一条，把该批注标记为 `<div class="rk-note is-done">` 并在账本对应行写明解决方案。批注本身是短期沟通载体，Agent 重写报告时会被覆盖，不需要长期保留——但它在账本里的登记必须留下。

批注同样适用上面四条纪律：不表演式赞同，不半懂就改，反查必要性，该顶回去就顶回去。

## 优先级

- 用户指令 > 本规则与 Skills > 默认行为
- 流程 Skill（`spec-*`）先于实现类 Skill 加载
