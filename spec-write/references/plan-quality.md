# plan 质量细则

`spec-write` 运行契约的「参考」行路由到本文件：plan 定稿前 → 必读。

本文件承载执行期细则，与 SKILL.md 的分工是：SKILL.md 说「必须过闸门」，本文件说「闸门怎么判」。

## plan 完备度闸门（四项）

`writer/plan.html` 定稿前，四项必须齐备。缺任一项不得进入实现阶段，`autopilot` 模式下同样不得自门禁放行。

| 项 | 判据 |
|----|------|
| 接口签名 | 每个新增或修改的函数/方法/接口写出完整签名：名称、参数名与类型、返回类型、抛出的错误类型。「返回处理结果」不算 |
| 数据结构 | 每个新增或修改的结构体/类/表/JSON 形状逐字段列出：字段名、类型、可空性、默认值。字段含义有歧义的补一句说明 |
| 文件清单 | 逐条列出要新建、修改、删除的文件路径。修改类要写清改哪个函数或哪个区块，不写「相关文件」 |
| 每任务验证命令 | 每个实现任务配一条可直接执行的验证命令，以及期望的观察结果（退出码、断言、输出片段）。命令必须是这个仓库真的能跑的 |

四项的检查结论逐条落账本，不写「已检查」这类无内容结论。

## Spec 自审四问

plan 写完、宣布定稿前，自己回答四个问题。任一问未过即返工，不带着问题进实现。

1. **占位符检查** —— 全文有没有 `TODO`、`待补充`、未替换的模板占位符（`{...}`、`XXX`、`<待填>`）？搜一遍，不靠印象。
2. **内部一致性** —— 前后章节有没有互相矛盾？典型冲突点：概述里的范围与任务清单不一致、数据结构章节的字段名与接口签名里用的名字不同、文件清单漏了某个任务要改的文件。
3. **范围检查** —— 有没有 plan 外的东西悄悄进来？逐条对回需求与探索报告：每个任务都能指回一条需求，不能指回的删掉或先问。
4. **歧义处理** —— 有没有哪句话存在两种读法？有就挑一个写明，并说明为什么挑它。歧义不能留给下游猜。

## 无占位符清单

以下表述在定稿的 plan 中一律禁止出现：

- `TODO`
- `待补充`
- `视情况而定`
- `类似的还有...`（以及「等等」「以此类推」这类省略）
- 未填的模板占位符（`{module_name}`、`XXX`、`<待填>`）

判据是机械的：搜到即不算定稿。真的还没想清楚的部分，不要用占位符掩盖，写成一条明确的待决问题交回 TeamLead。

## 任务定尺规则

每个实现任务必须能对应到**具体文件**与**具体函数/区块**。

- 合格：「在 `src/auth/session.ts` 的 `refreshToken()` 中加入过期重试，验证命令 `npm test -- session.spec.ts`」
- 不合格：「完善认证模块」「处理边界情况」「优化性能」

**写不出验证命令的任务，说明还没想清楚。** 这不是格式问题，是设计没做完：验证命令要求你先确定改动的可观察结果，写不出来意味着你还不知道改完之后拿什么判断对不对。此时的正确动作是把这个任务拆细或补做设计，不是先写进 plan 再说。

## 矛盾批量呈现

撰写过程中发现 plan 与探索报告、现有代码冲突时，**收集完一轮再一次性提出**，不要逐个打断用户。

做法：

1. 把冲突记进一张临时清单，每条写：冲突点、plan 里的说法、证据（文件路径 + 行号，或探索报告章节）、你倾向的处理。
2. 继续往下写，能绕开的先绕开，不能绕开的先按倾向方案写并标记。
3. 一轮撰写结束后，把整张清单一次性交回 TeamLead 或用户。

例外：冲突大到让整个方向失效（比如目标能力与现有架构根本冲突）时立即上报，不攒批。判据是「继续写下去的产出会不会全部作废」。
