3. Superpowers 实际内容（逐条核实）

3.1 三条独立纪律（可直接移植）

这三条各自靠顶部一条 Iron Law 生效，不依赖其他机制，是唯一可以单独摘出来的部分。

SkillIron Law 原文关键机制
skills/test-driven-development/SKILL.md NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST 验证 RED 三确认（失败而非报错 / 失败信息符合预期 / 因功能缺失而非拼写错）；验证 GREEN 三确认（本测试过 / 其他测试仍过 / 输出洁净无警告）；先写码则删掉重来，不留作参考
skills/systematic-debugging/SKILL.md NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST 四阶段各有出口条件；单一假设「I think X is the root cause because Y」并写下来；假设错了要形成新假设而非在旧修复上叠加
skills/verification-before-completion/SKILL.md NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE 五步门：IDENTIFY → RUN（完整、新鲜）→ READ（全量输出+退出码+失败计数）→ VERIFY → 才可声明。原文：Skip any step = lying, not verifying

三者共用一句基础原则：Violating the letter of the rules is violating the spirit of the rules.

3.2 测试有效性规则（首轮完全漏掉）

skills/test-driven-development/writing-good-tests.md 的内容比 SKILL.md 本身更可移植，且直接命中 R&K 的真实风险：

门函数：写测试体之前先回答

「什么样的生产代码改动会让这条测试失败？」——说不出来就重新设计测试。期望值必须是手工推导的字面量或 fixture，不能由被测代码或其 helper 算出来。

规则原文要点对 R&K 的意义
Mock 不配断言A mock assertion passes when mock is present, fails when absent—it says nothing about the component.直接可进 spec-execute 与 spec-review 的 Testing 检查项
Mock 数据要完整镜像部分 mock 会「静默通过而集成挂掉」——下游读到被省略的字段时测试仍绿R&K 现有测试规范未覆盖
生产类只带生产方法只被测试调用的 destroy() 属于测试工具，不属于生产类可进 .agents/rules/coding-style.md
断言源文本 = 假测试Asserting that a script, skill, or config contains an exact line proves only that the source is the source. 要运行产物并断言效果对 R&K 尤其关键：本仓库大量改的是 Skill 文档与 HTML 报告，最容易写出这种自证式假测试
面向 Agent 的文档怎么测由「消费该文档的 Agent 的行为」来测（指向 writing-skills）；纯人类散文不配测试这是 R&K 改 Skill 时唯一正确的验证路径，见 3.5

Phase 4.5 与 R&K「连续无进展」不是同一个信号

Phase 4.5 触发条件是：每次修复都有进展，但每次都在不同位置翻出新的共享状态 / 耦合，或修复要求「大规模重构」。原文断言 This is NOT a failed hypothesis - this is a wrong architecture。R&K 的 连续无进展（spec-debug/SKILL.md:197-199）抓的是「原地打转」，抓不到这种「一直在前进但方向错」的失败。两者必须并存，不能合并。

内容出处与要点

禁止表演式赞同receiving-code-review/SKILL.md：Code review requires technical evaluation, not emotional performance. 禁 You're absolutely right! / Great point! / 任何感谢表达。理由：Actions speak. Just fix it.
六步响应READ（读完不反应）→ UNDERSTAND（复述或问）→ VERIFY（对照代码现状）→ EVALUATE（对本代码库是否正确）→ RESPOND → IMPLEMENT（一次一项各自测试）

收尾顺序纪律先跑全量测试 → 绿了才出菜单 → 合并后在合并结果上再跑一次 → 失败则一切停住、分支与 worktree 原地保留

3.5 元技能：如何让规则真的被遵守

这是本次探索最重要的发现，也是决定整个改造成败的部分。skills/writing-skills/ 三份文件构成一套完整方法论。

核心洞察：写 Skill 就是对流程文档做 TDD

If you didn't watch an agent fail without the skill, you don't know if the skill teaches the right thing. 映射关系：压力场景=测试用例；SKILL.md=生产代码；无 skill 时 Agent 违规=RED；有 skill 时合规=GREEN；堵漏洞同时保持合规=REFACTOR。

压力测试构造法（writing-skills/testing-skills-with-subagents.md）：

  • 七种压力：时间 / 沉没成本 / 权威 / 经济 / 疲劳 / 社交（怕显得教条）/ 实用主义（「要务实不要教条」）
  • 最佳测试组合 3 种以上压力
  • 好场景五要素：具体 A/B/C 选项（非开放式）、真实约束（具体时间与后果）、真实文件路径、让 Agent 行动（「你会怎么做」而非「应该怎么做」）、无逃逸出口（不能靠「我会问人类伙伴」绕过选择）
  • 设置话术：IMPORTANT: This is a real scenario. You must choose and act.
  • 通过判据：最大压力下选对 + 引用 skill 章节作依据 + 承认诱惑但仍遵守。不算通过：找到新合理化说法 / 争论 skill 是错的 / 造「混合方案」 / 请求许可但强烈论证违规
  • 元测试三分法：Agent 选错后追问「这个 skill 该怎么写才能让 A 成为唯一可接受答案」。①「skill 很清楚，我选择忽略」→ 不是文档问题，加更强的基础原则 ②「skill 该说 X」→ 文档问题，原话加进去 ③「我没看到 Y 节」→ 组织问题，要点提前

说服原则（writing-skills/persuasion-principles.md）——这套解释了为什么「一张对照表」不会生效：

Skill 类型应使用应避免
纪律型（TDD、验证要求）权威（祈使句、「无例外」）+ 承诺（要求声明、强制显式选择）+ 社会认同（「每一次」、「X 没有 Y = 失败」）喜好、互惠
指导/技法型适度权威 + 统一（「我们是同事」）重度权威
参考型只要清晰全部说服术

伦理检验：Would this technique serve the user's genuine interests if they fully understood it?

尺寸预算：常驻/高频 skill <200 词，其他 <500 词，SKILL.md 正文 <500 行；重型参考（100+ 行）拆 references/。描述必须第三人称（因为被注入系统提示，人称不一致会破坏发现）。

3.6 强制力机制

hooks/session-start：每次会话读取 skills/using-superpowers/SKILL.md 全文，包进 <EXTREMELY_IMPORTANT> 标签，按运行时输出不同 JSON 格式注入上下文。即入口 skill 从第一条消息起就常驻，不是懒加载。

using-superpowers/SKILL.md 三块可移植结构：

  • 技能优先级：process skills come first — they set the approach, then implementation skills carry it out
  • 优先级链：用户指令（CLAUDE.md/AGENTS.md）> skills > 默认行为
  • <SUBAGENT-STOP>：被派作具体任务的 subagent 忽略入口 skill——R&K 七角色都是 subagent，需要等价规则防止每个角色重跑入口流程

3.7 SDD 簇（整体不可拆）

subagent-driven-development 的四个要素互为前提：每任务全新 implementer + 2–5 分钟任务粒度 + plan 内嵌完整代码 + 每任务两段 review（含 5 轮修复上限，R1–3 同一 implementer、R4+ 升级模型）。

但其中一条教训必须吸收

原文：账本必须落盘、不能只靠 todo，因为 conversation memory does not survive compaction；控制器丢账本导致重发整段已完成任务序列是他们观察到最贵的故障。这是对 R&K lead/team-context.md 设计方向的独立佐证——要补的只是「每个角色完成即写、不攒批」这条纪律。

4. R&K 现状与接收面

4.1 强制力三级（决定优先级排序）

最高优先级事实

所有 spec-* skill 都是 disable-model-invocation: true（已逐个 grep 确认：spec-start / write / execute / test / debug / review / end / explore / update / intent-confirmation / exp-reflect），只在角色显式调用时加载。OMP 下唯一每次会话自动进上下文的是 .agents/rules/（本次会话即通过 AGENTS.md 的 @import .agents/rules/ 装载）。只改 Skill 正文不改 rules，运行时行为不会变。

但 .agents/rules/spec-workflow.md 当前只有 9 行，且其中两行与双模式直接冲突：

  • 第 5 行「实现前必须有已确认的 writer/plan.html」
  • 第 7 行「每个关键节点等待用户确认」

自动驾驶模式在规则层非法，必须先把「确认」定义为含「用户确认」与「自门禁通过（带证据）」两义。另注：.claude/rules/ 只有 2 个文件而 .agents/rules/ 有 5 个，同步时易漏。

5. GPT r2 方案的事实错误（供 writer 避坑）

r2 的说法核实结果
「不引入 .superpowers/sdd/」，视其为要拒绝的 SDD 文件体系它是按 plan 分目录、git-ignore、最终 review 干净后 rm -rf 的临时工作区，唯一职责是 mid-plan compaction recovery。恰好是 R&K 账本的对标物，被当成要拒绝的东西
「不新增 Execution Capsule、JSONL Trace」仓库中不存在这两个概念。拒绝不存在的东西，占了「本次不包含」两条
「不改成固定五轮」（指调试）5 轮来自每任务 code review 修复循环（R1–3 同一 implementer、R4+ 升级模型），不是调试。调试的数字是 Phase 4.5 的「3 次修复失败」。Skill 与数字全挂错
「不把 Plan 写成含完整代码的超细脚本」writing-plans 明确要求 embedded code、no placeholders，因为 implementer 是零历史 subagent。而 R&K 的 spec-executor 在 OMP 下同样是 task spawn 的零历史 subagent（spec-init/references/project-agent-roles.md:116-117、:223-236）——同样病因，却把药拒了，同时还要求任务级 TDD
「不强制每个任务使用 Fresh Agent」答错了题。R&K 本来就是 fresh 角色；真正的差异是 per-task fresh implementer vs per-phase 单 executor

6. 对 Spec 创建的建议

建议一：方案按「接收方」组织，不按「七角色」组织

映射结果显示同一个 Superpowers skill 常要拆到多个 R&K 接收方（brainstorming → intent-confirmation + spec-write；writing-good-tests → spec-execute + spec-review + coding-style）。按角色组织会把它们打散。

建议二：纪律层不是「均匀撒在七角色上的一层」

正确结构是「一个门禁 = 一个验证器」：门禁模式下人是验证器；自动驾驶下每条纪律替代一个具体门禁。这样才能区分哪些纪律在门禁模式可放宽、哪些是自动驾驶硬底线。

建议三：优先级按强制力载体排，不按「改动大小」排

.agents/rules/ 必须 P0-1（唯一常驻面 + 当前规则与自动驾驶冲突）；skill-creator 必须早于任何「行为验证」步骤（它是压力测试法的宿主，现在零相关内容）。

可复用的现有组件：loop-design（表达自动驾驶 loop）、「修复循环预算」（预算机制）、各 Skill 的「运行契约」表（纪律落点）、spec-test 原则 6（证据自动生成）。

7. 已知风险与边界情况

风险 1：规则层非法

.agents/rules/spec-workflow.md:5,7 要求「实现前必须有已确认 plan」「每个关键节点等待用户确认」。自动驾驶违反现行项目规则。若不先改这条，整个模式在规则层站不住。

风险 2：spec-debug 存在自动驾驶死锁

spec-debug/SKILL.md:146：预算若为「待确认」，先停止并请 TeamLead 用 intent-confirmation 确认。自动驾驶下没有人可确认，此处直接卡死。必须规定自动驾驶取模式档案预设值。

风险 3：证据规则与 executor 拿测试所有权冲突

spec-test/SKILL.md:31 禁止 Agent 手写证据且要求落 tester/artifacts/。若让 executor 做 TDD 却只在 summary 里用自然语言总结「验证了什么」，正好落进这条禁令。必须给 executor 开 executor/artifacts/ 并套同一规则。

风险 4：测试质量出现两个 owner

若同时让 tester 审 executor 的测试质量、又给 reviewer 加 Test Quality 一栏，会造出职责重叠。另外 reviewer 要判 Test Quality 就得读 tester 产物，而 spec-review/SKILL.md:15 的输入只有 plan + summary + 代码，运行契约需同步改。

需 spec-tester 特别覆盖的边界

本次 Spec 按决策 D-005 只产出设计方案，不进入测试阶段。但方案的验收关注点必须是可机械判定的，不能写成「Agent 是否遵守」这类不可证伪的表述。建议两条：①扫账本决策记录，每行「依据」列必须匹配三种合法形式之一；②executor/artifacts/ 存在测试运行自动产出的 RED（含失败断言原文）与 GREEN（含退出码），且 summary 引用的命令与文件内容一致。

三处既存漂移（方案应列为待修项）

①分类目录名两套并存（spec-write/SKILL.md:47-52 vs 仓库实际）；②main 写死于 spec-start/SKILL.md 步骤 2 与 spec-end/SKILL.md:138，而仓库主分支是 master；③.agents/roles/ 完全缺失，spec-start 前置检查无法通过。
