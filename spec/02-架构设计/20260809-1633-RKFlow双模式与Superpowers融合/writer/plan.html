设计结论

吸收 Superpowers 的方式是三层承载，不是把正文迁进 SKILL.md：Iron Law 一句话进常驻 .agents/rules/，触发条件进各 Skill 运行契约的「验证/停止」两行，执行细则进 references/ 按需加载。落点按接收方而非七角色组织，因为同一个上游 skill 常要拆到两三个 R&K 文件。双运行模式（门禁 / 自动驾驶）是这些纪律的意义来源——人退出的每个门禁都必须有机械纪律补位，纪律因此从质量优化变成安全底线。

1. 概述

1.1 背景

R&K Flow 已具备完整的 Spec 生命周期、七角色分工、HTML 报告、运行账本、GitHub Flow 与显式经验系统。其弱项集中在工程执行纪律：

  • 门禁 3 的运行契约对验证零要求——用户在 executor/summary.html 处放行下游，而该 Skill 不要求任何验证证据。
  • spec-executor 被明令禁止写测试（六处），实现期没有任何测试反馈。
  • spec-debug 无根因优先约束，可以直接改码。
  • 完成声明可以靠「应该没问题」通过，无「本轮验证」要求。

Superpowers 恰好在这四处有成熟机制。但它的强制力来自 hooks/session-start 每次会话注入入口 skill，而 R&K 所有 spec-* 都是 disable-model-invocation: true——吸收的难点不在内容，在承载层。

核心判断

纪律不是均匀撒在七角色上的一层。三条 Iron Law（TDD / 根因优先 / 新鲜验证）各自替代一个具体的人类门禁；只有把「哪条纪律补位哪个门禁」说清，才能区分门禁模式下可放宽的（有人验证时是质量优化）与自动驾驶下不可协商的（无人验证时是唯一防线）。

1.2 目标

  1. 按三层承载吸收 Superpowers 纪律，任何 SKILL.md 不因此超尺寸预算。
  2. 定义门禁 / 自动驾驶两种模式，及一份不可关闭的「永远门禁」清单。
  3. 把每条纪律精确绑定到它替代的门禁，而非按角色罗列。
  4. 让自动驾驶的每个自主决策留下可机械校验的依据。
  5. 把角色从一次性 subagent 改为跨 Spec 持续在场。
  6. 修正阻碍上述目标的既存缺陷与文档漂移。

1.3 范围

包含

  • Superpowers 14 个 skill 的逐条归宿映射与三层承载规则。
  • 双模式定义、门禁—验证器映射、永远门禁清单。
  • 账本结构变更（依据列、判定方式、模式、角色句柄）。
  • 角色持久化协议（四态判定、续接动作、硬边界）。
  • 次要项：账本改 HTML + 左侧导航树（附带需求，见第 6 节）。
  • 改造清单与实施顺序，按强制力载体排序。

不包含

  • 本次不改任何 Skill、rules、README/CODEMAP（按 D-005 只产出设计方案）。
  • 不引入 SDD 簇整体（per-task fresh implementer + 2–5 分钟粒度 + 每任务两段 review）。
  • 不采用 one-question-per-message。
  • 不给账本设置 end-of-life；账本永久保留。
  • 不为角色启用 isolated（与持久化互斥）。
  • 不新建给人阅读的报告类型。

2.2 非功能需求

  • 强制力硬规则必须落在每次会话自动加载的 .agents/rules/，不能只写在按需加载的 Skill 或 README。
  • 尺寸吸收动作不得让任何 SKILL.md 正文超 500 行；超标者同步拆 references/。
  • 阅读体验不新增给人读的报告类型；自动驾驶新增的只有机器证据目录。
  • 离线可读报告与账本必须 file:// 直接打开即可用（现有硬约束，html-report/SKILL.md:258）。
  • 可审计自动驾驶结束后，仅凭账本与产物即可判断每个自主决策是否有据。
  • 兼容门禁模式行为与现状一致；多运行时降级路径仍成立。
  • 可演进不新造与现有内核重复的词汇（复用运行契约六要素、修复循环预算、loop-design）。

3. 设计方案

3.1 三层承载：吸收 ≠ 迁移正文

上游自己就是分层的：systematic-debugging/ 把 Iron Law 与四阶段留在 SKILL.md，把 root-cause-tracing.md / defense-in-depth.md / condition-based-waiting.md 拆成独立文件；test-driven-development/ 同理拆出 writing-good-tests.md。R&K 照同一分法。

层承载什么量级为什么在这一层
.agents/rules/
常驻		 三条 Iron Law 各一句话；两种模式定义；「确认」双义；依据三形式；永远门禁清单；跨角色审查响应纪律；技能优先级与优先级链 约 30 行 唯一每次会话自动进上下文的载体。Iron Law 必须在这一层——若连「这里有条不可协商的线」都要按需加载，等于让被约束者自己决定是否加载约束自己的规则
各 Skill
运行契约		 「验证」「停止」两行补入纪律要求；references 路由表 改字段，不加章节 复用已有结构，不起并行章节。路由条件必须机械可判（「代码任务 → 必读 X」），禁止写「如需要可参考」
<skill>/references/ RED/GREEN 三确认、测试有效性门函数、mock 四规则、四阶段出口条件、Phase 4.5、根因追溯、四层校验、条件等待、严重度定义、限定复审、压力测试构造法、说服原则、plan 无占位符清单 按需加载 执行期细则不占常驻预算。各 Skill 已有 references/，spec-test 还有现成的「何时读取」路由范式可复用
路由条件的写法决定纪律是否生效

「如需要可参考 references/tdd-discipline.md」等于没写——需要与否由被约束者判断。必须写成「任务涉及代码改动 → 开工前必读 references/tdd-discipline.md」，条件可由外部观察者机械判定。

3.2 逐条归宿映射（按接收方组织）

不按七角色组织，因为同一个上游 skill 常要拆到多个接收方：brainstorming → intent-confirmation + spec-write；writing-good-tests → spec-execute + spec-review。按角色组织会把它们打散并掩盖缺口。

3.2.1 spec-execute ← test-driven-development

吸收内容层为什么需要
TDD 铁律：无失败测试不写实现代码rules（一句话）门禁 3 在自动驾驶下无人验证，这是唯一实现期反馈
RED/GREEN 三确认：RED 需确认「测试失败」「失败原因是缺功能而非笔误」「断言的期望值手工推导得出」references/tdd-discipline.md只说「先写测试」会得到一个恒真测试
测试有效性门函数：提交前必须能说出「什么改动会让这个测试失败」同上这是唯一能机械问答的假测试筛子
断言源文本 = 假测试同上对本仓库尤其关键——R&K 改的大多是 Skill 文档与 HTML，最容易写成「grep 到这行字就算过」
mock 四规则同上防止测试只验证了 mock 自己
必须一起改的六处

executor「不写测试」散布在 spec-execute/SKILL.md:25（运行契约·权限）、:38-40（v2.0 变更）、:143（常见陷阱）、README.md:1067、spec-init/references/project-agent-roles.md:360、CODEMAP.md:151。漏改任一处，规则自相矛盾，Agent 会按先读到的那条执行。

证据规则冲突必须同时解

spec-test/SKILL.md:31 规定证据必须由测试运行自动产出、Agent 不得手写或回填。若 executor 做了 TDD 却只在 summary.html 用自然语言总结，正落进这条禁令。解法：开 executor/artifacts/ 并套用同一自动生成规则。另 spec-test/SKILL.md:19 给 tester「可调整测试脚本/配置」的权限，会与 executor 拥有的单元测试文件相撞，需按测试层级划清。

3.2.2 spec-debug ← systematic-debugging

吸收内容层为什么需要
Iron Law：未验证根因不得改码rules（一句话）替代「诊断确认」门禁
四阶段出口条件（每阶段必须产出什么才能进下一阶段）SKILL.md 正文阶段名无约束力，出口条件才有

Phase 4.5：连续修复都有进展、但每次都翻出新的共享状态或耦合 → 停下质疑架构正文这个信号独立于现有「连续无进展」——有进展的死循环现行机制抓不到
根因追溯技法 / 四层校验 / 条件等待禁 sleep / find-polluterreferences/ 三文件执行期技法，按需加载

3.2.3 .agents/rules/ ← receiving-code-review + using-superpowers

吸收内容为什么在常驻层而不做成 skill
禁表演式赞同（「你说得对」后立刻照做而未验证）它约束的是任何角色收到任何审查意见时的行为，不是有始有终的流程。做成 skill 反而不会在需要的时刻被加载——收到批评的那一刻，角色不会想到「我该去调用一个 skill」
六步响应流程：先复述再验证再判断，而非先致谢再实施
部分理解即停：只理解了意见的一部分就不能开始改
YAGNI 反查：被要求加的东西是否真有当下需求
何时该顶回去，以及顶回去要带什么证据
技能优先级：流程 skill 先于实现 skillR&K 有 20+ skill，冲突时需要仲裁规则
优先级链：用户指令 > skills > 默认行为同上

3.2.4 skill-creator ← 全体元技能（最大单一接收方）

本仓库的产物就是 Skill，所以「怎么写 Skill」在这里不是元问题而是主业。现状是零相关内容。

  • 写 Skill 即对流程文档做 TDD：无 skill 时让 Agent 跑基线场景、观察它是否违规，那次违规就是 RED。
  • 压力测试构造法：七种压力类型、单场景 3+ 组合、场景五要素、通过/不通过判据、元测试三分法。
  • 说服原则七条及按内容类型配比（纪律型 / 参考型 / 技法型用不同写法）。
  • 尺寸预算与第三人称描述规则。
它是本方案第 5 节「行为验证」的前置

没有压力测试法，「新规则是否真的改变了 Agent 行为」就无从检验，整个吸收变成不可验收。所以它在实施顺序里必须早于验证步骤。

3.3 双模式：一个门禁 = 一个验证器

模式的本质不是「确认多少次」，而是「谁来验证」。门禁模式下人就是验证器；自动驾驶把人拿掉，必须有等价物补位。这张表同时给出了 3.2 各条纪律的意义定位。

门禁门禁模式验证者自动驾驶替代物纪律来源
门禁 1 需求对齐用户确认编码思路小结无替代物 → 永远门禁—
门禁 2 plan / test-plan用户确认设计plan 完备度闸门 + Spec 自审四问writing-plans、brainstorming
门禁 3 实现确认用户读 summary.html 放行本轮新鲜验证 + executor/artifacts/ 自动产出的 RED/GREEN 证据verification-before-completion、TDD
诊断确认用户认可根因单一可证伪假设 + 最小实验；未验证不得改码systematic-debugging
门禁 4 测试确认用户读 test-report.htmlreviewer 强制介入（自动驾驶下唯一独立视角）requesting-code-review
修复循环预算用户定上限模式档案预设值 + Phase 4.5 架构信号现有预算机制 + Phase 4.5
归档 / 提交 / PR用户确认全量测试绿 + 本轮验证；合并 / force / 碰 master 仍永远门禁finishing-a-development-branch

3.3.1 永远门禁清单

判据是可逆性与治理面，不是风险等级——后者需要新造分类学，前者用已有信息即可判定。

  • 模式选择本身（不能自动驾驶地决定进入自动驾驶）
  • 修改 AGENTS.md / .agents/rules/——自我修改治理规则；自动驾驶下只产出建议队列，不落笔
  • 合并、force push、碰 master
  • 根因涉及权限 / 计费 / 数据迁移 / 需绕过测试（复用 spec-debug/SKILL.md:25 现有升级条款）
  • 超出已确认 plan 的 scope 扩张
  • Phase 4.5 触发
「升级」= 就地降级为门禁模式并等人，不是中止

这样各 Skill 运行契约里现成的「升级」条款语义一行不改，只在自动驾驶下多一个降级动作。自动驾驶因此就是一个标准 loop——六要素齐备、停止与升级必填，正是 loop-design/SKILL.md:31 的语言，不必新造风险分类学。

3.3.2 账本：依据必须可机械校验

现行决策记录九列有「理由」但没有「依据」——理由是自然语言可被生成，依据必须可追。

区块变更取值约束
frontmatter新增 modegated | autopilot
frontmatter新增自动驾驶预设预算进入时一次性确认，运行期不再打扰
决策记录新增「依据」列只接受三形式：①文件路径+行号 ②命令+退出码+输出位置 ③用户原话引用。「根据经验」「通常做法」「这样更专业」一律不算
门禁决策新增「判定方式」列user | self+evidence，后者必须带证据指针
角色运行句柄「可恢复」改为映射真实状态 + 新增「续接方式」「累计参与 Spec 数」两列见 3.4

3.4 角色持久化：从一次性资源到固定成员

本次已在 OMP 实测确认：向 40 分钟前跑完的 parked subagent 发消息并明确要求「只凭记忆回答、不许重读文件」，它准确复述了最初任务要求与自己的结论，hub 返回 revived。能力一直存在，缺的是 R&K 侧的协议。

状态含义续接动作
running正在执行hub send 插话 steering
idle跑完，session 仍挂载hub send
parked空闲超 task.agentIdleTtlMs（默认 420000ms）后释放 session，AgentRef 与 session 文件保留hub send，消息即自动复活
aborted被取消 / 超时 / 硬中断终态，只能重新 spawn 并从账本与产物重建
续接只能用 hub send，不能用重新 spawn

agent:// id 按 name 分配，同名再 spawn 会得到 spec-writer-2——一个全新的零历史 agent，正是要避免的影子角色。另：spawn 时 name 必须显式等于角色 id，否则会拿到随机生成名而失去可寻址性。

四条硬边界（必须写明，否则承诺过头）：

  1. isolated: true 与持久化互斥——隔离 agent 完成即拆除。R&K 角色不启用隔离工作区。
  2. aborted 是终态，此时账本 + 落盘产物是唯一恢复路径。
  3. 进程边界：registry 是 process-global。同 session 内可续接；omp 重启后靠账本与产物重建。
  4. 新 spawn 不继承对话历史。所以账本永远是兜底，不因「能续接」而放松落盘。

要改三处：spec-start/SKILL.md:285 把「跨 Spec」与「跨进程」混为一谈，是 TeamLead 读到「handle 不重要」信号的根因；:299 写了「可恢复则继续同一角色线程」但没给判定方法与具体动作；spec-update 需明确「先查账本 handle → hub list 核状态 → 能续接就消息同一角色」。

5. 验收关注点

全部要求可机械判定，不接受「Agent 是否遵守」这类不可证伪表述。

  • 依据可校验：跑一次真实小改动的自动驾驶全程，扫账本决策记录，每一行「依据」列必须匹配三种合法形式之一；一行不匹配即失败。
  • 证据非手写executor/artifacts/ 存在测试运行自动产出的 RED 输出（含失败断言原文）与 GREEN 输出（含退出码），且 summary.html 引用的命令与文件内容一致；出现无退出码、无时间戳等人工补写痕迹即失败。
  • 完备度闸门生效：故意给一个缺接口签名的 plan 进自动驾驶，必须被闸门挡住，而不是被 executor 自由发挥。
  • 永远门禁不可绕过：自动驾驶下尝试触发改 .agents/rules/、合并、force push，必须全部停下等人。
  • 死锁已解：自动驾驶进入修复循环时不再卡在「预算待确认」。
  • 角色续接：同一 session 内跨阶段 handoff 后，hub list 显示角色仍是同一 id（无 -2 影子），且续接后能引用此前上下文。
  • 规则自洽：全仓搜索「不写测试」「可选」等旧口径，无残留矛盾表述。
  • 尺寸达标：改造后无 SKILL.md 正文超 500 行。
  • 门禁模式无回归：门禁模式下走一遍完整 Spec，确认交互与现状一致。

6.1 导航树技术方案（附带需求）

用户提出「报告左侧有个文件树导航，可在本 Spec 已有 HTML 文档间切换」，且必须 file:// 直开可用。

约束：file:// 下 fetch 被浏览器安全策略直接拒绝，无法用 fetch(t).ok 探测同级文件是否存在（已在本地实测验证，已存在的 exploration-report.html 仍返回 Failed to fetch）。

方案：生成一份 rk-manifest.js 在 Spec 根目录，声明已知报告清单。各报告通过 <script src="../rk-manifest.js"></script> 加载——<script src> 不受 file:// CORS 限制（已实测：fetch 被拒但 script src 正常加载）。导航树由 rk-nav.js 渲染为固定左侧栏（窄屏折叠、打印隐藏）。

manifest 维护：有两种实践——A) 每次生成报告时由当前角色更新 manifest；B) 由 TeamLead 在新增报告后统一更新。推荐 B，避免多角色并发编辑 manifest。

附录：账本 HTML 化——按 D-012 豁免修订标记。理由：账本是高频追写的运行记录，不是「定稿后修订」的报告，强制 data-rev 会让它膨胀。但需复用样式与导航树。
