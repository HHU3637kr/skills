# EXP-004：红蓝对抗式审查规程与深水区缺陷防伪验法则

## 1. 困境背景
在复杂技术基建与跨组件协作集成中（如 R&K Flow 接入 AWR 运行时），常规审查极易滑入“形式化放行”与“假闭环”陷阱：
1. **伪兜底与静默吞错**：用 `|| true`、空 `try...catch` 掩盖底层致命错误，导致进度静默丢失且上游无感知；
2. **状态机与行正则截断**：流式行解析（如 awk/grep）处理嵌套 JSON 时，子数组闭合括号提前终止状态机，导致真实缺陷 100% 漏检；
3. **Shell 控制流伪阻断**：子进程 `sys.exit(1)` 退出后，外层 Shell 若未通过 `if ! ...; then exit 1; fi` 捕获，脚本依然静默继续执行；
4. **声称与机器状态脱节**：将文档级源引用误当成已完成的数字签名，产生假完工。

## 2. 核心审查立场（Red Team Stance）
- **保持中立客观，优先指出方案的缺陷与不足**，严禁盲目附和与形式化夸赞；
- 绝不轻信“代码看起来没问题”，每一项审查必须基于**对抗性反例构造与实测复现**；
- 给不出具体失效场景、复现代码或依据的审查意见不构成有效结论。

## 3. 核心核验法则
1. **实测复现先行（Reproduction First）**：
   - 评审任何边界问题时，先写最小测试用例在沙箱中复现并观察控制台输出，拿确凿退出码和报错日志说话。
2. **兜底路径必查（Fail-Closed Verification）**：
   - 重点审查降级分支与异常捕获块，坚决消灭把错误“洗成 0 / 放行”的 fail-open 逻辑；
   - 缺少关键解析工具时直接阻断退出，不进行不可靠的模糊猜测。
3. **严格区分声称与机器状态**：
   - 静态文档（YAML/Markdown）中的标记不等于底层数据库的数字证据；
   - 审查完成声明时，必须以工具实际返回的状态（如 `awr work show`、`git status`）为准。
4. **用当初抓漏洞的同一方式验修复（Symmetric Verification）**：
   - 修复缺陷后，必须用当初捕获该漏洞的同一套反例样本与脚本控制流再次实跑验证；
   - 绝不可用“简化了的、假定成功”的弱断言替代真实复现验证，严防“把一个 Bug 换成另一个 Bug”。
