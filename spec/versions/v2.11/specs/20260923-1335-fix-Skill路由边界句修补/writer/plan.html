1. 目标与非目标

1.1 目标

  1. 闭合 4 条已实测的中文请求错判（r02 改 plan.html 漏参数、r08 沉淀记忆、r13 核对用例真跑、r06 线上故障诊断修复）。
  2. 给 8 个 skill 补齐成对的边界句——两侧同时改，避免把边界单方面推给某一方造成新的不对称。
  3. 保持 description ≤1024 字符、frontmatter 可解析、name 不变。

1.2 非目标

  • 不改 .agents/rules/、README.md、CODEMAP.md、任何流程 Skill 正文（永远门禁 + 范围控制，见账本 D-004）。
  • 不做 skill 自动装载改造（本仓库全部 disable-model-invocation: true，改动运行时要另行立项）。
  • 不重写 description 的原有语义句，只做边界追加与两处定向重写（html-report、spec-start，理由见 §3.3、§3.6）。

3. 逐条变更集（8 个 SKILL.md frontmatter）

规则：原文逐句保留；新增句置于语义相邻处；spec-start 与 html-report 为定向重写（原文含义全部保留，仅收窄触发面）。

3.1 spec-test/SKILL.md:4-8 —— 补「证据核对」触发面

追加：也用于核对用例与证据是否真跑过：校验测试是否在当前工作树实际运行、证据是否由测试运行自动生成（禁止事后手写补写）、识别假测试假绿与测试有效性、评估 spec-executor 的单元测试质量。；负面句保持「不要用于普通代码实现或 bug 修复」。

3.2 spec-review/SKILL.md:4 —— 补对侧归属

追加：不要用于核对用例或证据是否真跑过、识别假测试与评估测试质量（归 spec-test），也不要用于运行期故障诊断与 bug 修复（归 spec-debug）。

3.3 html-report/SKILL.md:3-11 —— 重写为格式契约口径

首句收窄为「…Spec 报告（exploration-report / plan / test-plan / test-report / summary / debug / review / update / end-report）的格式时使用」；典型信号加「核对修订号/修订历史/meta/双向关联/样式表是否符合契约」；新增两条边界：

  • 本 Skill 只规定"报告长什么样"，不决定"报告里写什么"：补漏需求参数、改方案、调整验收标准、修结论、补修订历史内容分别属于 spec-update / spec-write / spec-execute 等角色 Skill，它们只在需要遵守格式契约时读本 Skill。
  • 请求里出现 report/plan/update 等文件名不构成本 Skill 的触发条件。

「不要用于记忆库文件（spec/context/**/*.md…）」原句保留。

3.4 spec-update/SKILL.md:4 —— 补用户向触发词

在入口句与「默认复用 git_branch」之间插入：

  • 典型信号："改 writer/plan.html 里漏掉的分页参数""补一条原 Spec 没覆盖的需求""修 update 方案里写错的验收标准"、修订既有 writer/plan.html / executor/summary.html、给已有报告递增修订号并补修订历史行（5 列格式与 <ins>/<del> 标记规则由 html-report 定义，写什么内容、为什么归本 Skill）——只要动的是报告所承载的 Spec 内容，就走本 Skill；请求里出现 report/html 字样不改变归属。
  • 只关心报告骨架、样式表、修订标记或 meta/双链格式本身时改用 html-report。

3.5 exp-reflect/SKILL.md:4 + exp-write/SKILL.md:4 —— 落盘责任切开

exp-reflect 追加：本 Skill 只做识别 + 分类 + 权重判断 + 草稿 + 用户确认，不落盘写入；内容已经明确、只需写入经验/知识文件并更新索引时直接用 exp-write。

exp-write 重写触发行（原文「触发场景：exp-reflect 确认后、手动添加经验或知识」的三个入口全部保留并显式化）：触发场景：/exp-write type=experience、/exp-write type=knowledge 手动写入，exp-reflect 确认后落盘，或用户要求把内容已经确定的经验/知识写进记忆时使用，典型信号："把这次 AWR 踩坑写进经验记忆""把架构调研整理成知识记忆""把 exp-reflect 确认过的草稿写入索引"。，并加 本 Skill 只执行写入；判断是否值得沉淀、归哪类记忆、去重与草稿生成由 exp-reflect 负责，需要先识别分类时用 exp-reflect。

3.6 spec-start/SKILL.md:4-6 —— 负面清单补 debug

末句由「不要用于已有完成 Spec 的小迭代（用 spec-update）或项目首次初始化（用 spec-init）。」扩为「…运行期故障诊断与 bug 修复（用 spec-debug），或不需要启动 Spec 流程的纯文档/记忆写入（用对应 Skill）。」

3.7 spec-debug/SKILL.md:4-8 —— 补用户向触发词

触发条件追加第 (4) 条 用户要求诊断/修复线上问题、偶发故障、异常报错、环境依赖问题或回归排查；末尾追加 触发词：诊断、修复、线上问题、偶发 500、复现、回滚。主动迭代新需求归 spec-start / spec-update。原文「不修改已确认的 writer/plan.html…由 TeamLead 启动 spec-tester」等句全部保留。

4. 实现步骤

  1. RED 先行：在未打补丁的 HEAD 描述上跑 26 条 gold 基准，必须观测到 ≥3 条错判（r02/r06/r08/r13 至少中 3 条），留存 tester/artifacts/test-logs/<run-id>/red-route-bench.log。
  2. 应用补丁：按 §3 逐条改 8 个 SKILL.md frontmatter，只改 description 块，其他字节不动。
  3. 静态自检：8 个文件 frontmatter 可解析、name 不变、description ≤1024、原文句子未被删（逐句包含审计）。
  4. GREEN：同一基准在补丁后工作树上重跑，目标 26/26（允许 1 条兜底类抖动，抖动项不得是原错判）。
  5. 改动面断言：git diff --name-only 恰为 8 个 SKILL.md（不含 .agents/rules/、不含 roster 其余 14 个）。

5. 测试策略（详见 tester/test-plan.html）

  • TC-01 行为基准（RED→GREEN）：26 条中文请求 × judge Choice 路由，gold 写死；RED ≥3 miss，GREEN ≥25/26。

  • TC-03 边界双向性：4 组边界的每一侧都显式点名对侧 skill 名。

  • TC-05 抖动复跑：GREEN 复跑一次，记录 flap 项并判定是否落在原错判集合。

6. 风险与回滚

风险影响缓解
边界句写得太长，反而稀释主触发条件原本正确的请求被推走TC-01 的 12 条反向探测项（必须仍归 html-report/exp-search/exp-reflect/spec-test/exp-write）即防过纠；修后复跑 25-26/26 已验证
「报告内容 vs 格式」边界仍有一类模糊表述（纯修订历史表操作）r16 类请求偶发判偏已实测：补「递增修订号并补修订历史行…归本 Skill」后 r16/r22 均正确；残余抖动记录在测试报告，不作为本次验收项
改 description 影响下游已克隆项目的 skill 列表展示仅展示文本变化，无行为变化只追加/收窄描述，不增删 skill、不改 name
回滚—单 PR 内 git revert 即回到 18/26 状态；无数据/结构迁移

7. 验收标准（对应 AWR 台账 acceptance 原文）

  1. 8 个 SKILL.md 的 description 补齐与对侧 skill 的显式职责边界句，frontmatter 可解析、name 不变、description 不超过 1024 字符。
  2. 26 条中文请求路由基准在修补后的工作树上全绿；同一基准在修补前至少 3 条错判。
  3. roster 其余 14 个 SKILL.md 与 .agents/rules/ 零改动。
