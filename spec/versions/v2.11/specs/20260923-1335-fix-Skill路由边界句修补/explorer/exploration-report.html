2. 三个已知错判的根因

2.1 「改 writer/plan.html 漏的分页参数」→ 误判 html-report

根因：html-report/SKILL.md:3-11 的 description 自称「当需要产出或修改 R&K Flow 的 Spec 报告（…plan…update…）时使用」，并把「要修订已有报告」列为典型信号；而 spec-update/SKILL.md:4 只说「修正方案或优化实现」，全文没有一处出现「修改 writer/plan.html 这个文件」的用户向说法。请求里同时出现文件名 writer/plan.html 与动词「改」，词面命中 html-report。

性质：格式契约 skill（README.md:523 定位为「所有报告类产物的格式基础」）的触发条件写得像任务 skill，与每一个产出报告的 spec-* 角色都重叠。

2.2 「把 AWR 踩坑沉淀到记忆」→ 误判 exp-reflect

根因：「沉淀」是 exp-reflect/SKILL.md:4 的原词（「判断是否沉淀经验、知识、SOP…」）；而 exp-write/SKILL.md:4 的 description 是角色自述（「记忆写入 Skill，将重大经验写入…」），触发条件全部是内部调用（「exp-reflect 确认后、手动添加经验或知识」），没有一条用户可见入口。请求由用户直接发起且内容已明确（AWR 踩坑），应走 exp-write 落盘。

2.3 「核对 tester 用例是否真跑过」→ 误判 spec-review

根因：spec-test/SKILL.md:4-8 的 description 只覆盖「写 test-plan / 跑测试出 test-report / 修复后重验」，没有「核对证据是否真跑、识别假测试假绿、评估测试质量」——而这些恰是它 body 里的硬规则：spec-test/SKILL.md:20「最终测试结论必须基于本轮在当前工作树上的实际运行」、:32 证据必须自动采集禁止手写补写、:23 评估 spec-executor 单元测试质量。请求落在该缺口，被 spec-review/SKILL.md:4 的触发词「检查实现」「审查 Spec」接走。

2.4 同型第 4 例（本次扩展实测发现）：spec-start 吞掉 spec-debug

现象：「线上分页接口偶发 500，帮我诊断并修复」被判为 spec-start。

根因：spec-start/SKILL.md:4-6 的入口只有「开始新的开发任务…启动完整 Spec 流程」这一宽口径，负面清单仅列了 spec-update 与 spec-init，没有把运行期故障诊断/bug 修复挡给 spec-debug；spec-debug/SKILL.md:4-8 的触发条件又全是角色内部视角（「角色 spec-debugger 接收到 TeamLead 转交的 bug handoff」），缺用户向触发词。

佐证：README.md:481 已明确 update 用于主动迭代、debug 用于被动修复 —— 说明边界本身在仓库里有共识，只是没写进 description。

5. 运行时影响面

  • 本仓库 52 个 SKILL.md 全部带 disable-model-invocation: true（README.md:1432 记 38 个后持续增长），运行时不做 skill 自动装载；因此 description 的错判不会造成「自动载错 skill」，但它是人/agent 扫 roster 选 skill 时的唯一机器可读边界信号（.agents/rules/spec-workflow.md 与 .agents/roles/ 均不做路由）。
  • 修补只动 frontmatter 文本，不改任何流程铁律、不改 .agents/rules/，因此不触发「永远门禁」。
  • 长度约束：修后最长 spec-update 536 字符，全部 ≤1024（darwin-skill rubric 上限）。
