# 用户视角状态机与不变量审查

`spec-review` 运行契约的「参考」行路由到本文件：涉及多状态流转、异步重试、并发重入、权限切换或复杂 UI 交互态时必读。

本协议借鉴 `pstack` `/statechart` 思路，用 `html-report` 原生内联 SVG（`figure.rk-fig`）从**用户/业务视角**呈现状态机与不变量检查结果，让审阅者无需通读底层代码即可看清违规与缺失路径。

---

## 1. 何时启用与跳过规则

| 条件 | 处置 |
|------|------|
| **触发启用**：满足任一即启用 | ① `writer/plan.html` 3.1 节列出了「核心不变量」<br>② Spec 涉及多状态流转（订单、任务、审批、会话、连接、离线同步等）<br>③ 涉及异步重试、超时降级、并发竞争或重入控制<br>④ 涉及角色/状态驱动的权限切换或复杂多态 UI 交互 |
| **跳过条件**：无上述特征 | 纯静态文案/配置、无状态纯函数、简单单表 CRUD——在 `reviewer/review.html` 的「2.2 核心不变量与用户视角状态机」小节保留标题，写明「不适用（本次无状态流转）」，不硬画图 |

---

## 2. 四步审查协议

### 步骤 A：提取不变量（Invariants）

1. **优先继承设计约定**：直接读取 `writer/plan.html` 3.1 节「核心不变量」表（`INV-001` 等）。
2. **缺失时反向提炼**：若 `plan.html` 未单列，从 `writer/plan.html` 的验收标准、业务规则与 `tester/test-plan.html` 的边界矩阵中提炼 **3–7 条**核心规则。
3. **陈述规范**：每条不变量必须用**用户或业务语言**表达（例如：「已取消的订单不能再次进入支付成功状态」「断网重连后未提交草稿不得静默丢失」），不得写成代码函数名或内部标志位条件。
4. **禁止削弱规则**：发现实现难以满足某条不变量时，必须把问题记为发现项；严禁为了迁就现有代码而改写或放宽不变量定义。

---

### 步骤 B：从实现代码反向抽象用户视角状态机

1. **只反映实际代码**：状态与转移必须来自对当前实现代码的实际核对（而非直接抄 `writer/plan.html` 的理想设计），这样才能暴露实现漏判或非法转移。
2. **用户视角命名（严禁泄露内部实现词）**：
   - 节点标签写**用户可见或业务关心的状态**（如 `待支付`、`重试等待中`、`离线草稿`、`已取消`），禁止出现 `isLoading === false`、`retryCount > 0`、`stateFlag` 等代码符号；
   - 箭头标签写**用户动作或外部事件**（如 `点击取消`、`网络超时`、`支付回调到达`）；若同一动作仅在特定条件发生，可用方括号补充用户可见条件，如 `点击重试 [离线中]`。
3. **复杂度控制（对齐 `html-report/references/figures.md`）**：
   - 控制在 **≤ 12 个节点、≤ 20 条边**，避免画成无法扫读的网状图；
   - 状态过多时，先合并「对外表现与后续转移完全一致」的中间态，或在 `<figcaption>` 中说明被隐藏的全局重置/常规回退转移；
   - **禁止合并违背不同不变量的状态**，以免掩盖真正出错的状态位置；若单一流程超过 12 个节点，拆成「主流程总览 + 违规局部放大」两张图。
4. **重点搜寻四类高危缺陷**：
   - **非法转移**：某个状态在特定事件序列下走到了不变量禁止的状态；
   - **死状态 / 死锁**：非业务终态的节点在实现上没有任何可恢复的出边；
   - **缺失异常回退**：异步请求失败、超时或并发取消后，状态卡死在中间态（如永久 `处理中`）；
   - **竞态交叉**：前一次操作回调晚到，覆盖了用户后一次动作产生的新状态。

---

### 步骤 C：用 `figure.rk-fig` 内联 SVG 渲染进 `reviewer/review.html`

严格遵循 `html-report/references/figures.md` 的画法约束（不写死 `fill="#..."` / `stroke="#..."`，不使用行内 `style=`，`<svg>` 必须有 `role="img"` 与 `aria-label`，多图时 `<marker id>` 递增不重复）：

1. **语义上色映射**：

| 状态/转移语义 | SVG class | 含义（对照 `pstack` `/statechart`） |
|---|---|---|
| 正常中间态 / 入口态 | `node` | 常规状态节点，白底灰边 |
| 正常终态 / 已验证安全态 | `c-green` | 业务终态或实证符合全部不变量 |
| 风险可疑态 / 缺证据态 | `c-amber` | 对应 `mayBreak`：部分条件路径可能违规，或缺少实测覆盖 |
| 违规态 / 死状态 / 缺失异常回退 | `c-red` | 对应 `breaks`：明确违背某条不变量，或卡死无出边 |
| 正常转移 / 缺失或违规转移 | `edge` / `edge dash` | `edge dash` 用于标出非法跳转或「应有但实现缺失」的异常回退 |

2. **配套「不变量与最短违规路径」表**：
   图后必须紧跟检查表（5 列：`不变量 | 用户视角规则 | 结论 | 最短触发路径 | 代码位置与证据`）。
   - 每条违规或存疑路径必须写出**从初始态出发的最短触发步骤**，格式示例：`待支付 → 点击取消 → 支付回调延迟到达 → 已支付（违背 INV-001）`；
   - 结论未通过或可疑时，在「代码位置与证据」列给出 `<span class="rk-ref">file:line</span>` 与对应的实测探针输出（未实测须显式标 `[INFERENCE]`），并同步在「4. 问题清单」登记定级。

---

### 步骤 D：可选重型扩展（高风险并发 / 协议 Spec 的 TLA+ / TLC 形式化检查闭环）

仅当 Spec 涉及**分布式一致性、跨端同步、资金/库存原子扣减、复杂锁/租约或常规单测难以触达的并发交错**时按需启用，常规业务 Spec 不强制。

1. **独立临时目录运行**：在仓库外临时目录（如 `$TMPDIR/statechart-check/`）编写 `.tla` 模型与 `.cfg` 配置（把每条核心不变量写为 `INVARIANT`），运行 TLC 模型检测器（或 `pstack` `/statechart` 脚本）穷举状态空间。
2. **提炼可读结果**：把模型检查发现的反例最短路径与状态总数摘要写入 `reviewer/review.html` 2.2 节，并明确标注模型边界与假设（例如并发客户端数上限、最大重试次数）。
3. **强制真实代码回放铁律**：
   - 模型发现的每条违规路径，**必须在真实代码上逐步回放验证**（通过只读沙箱探针或新增最小复现单元测试脚本观察真实行为）；
   - 如果真实代码无法复现模型报错，**优先怀疑抽象模型与代码语义不一致**，不得把未回放证实的模型报错直接判为 `blocker`；在未回放确认前，一律标为 `[INFERENCE]` 并说明差异点。
