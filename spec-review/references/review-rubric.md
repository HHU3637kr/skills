# 审查评级与清单

`spec-review` 运行契约的「参考」行路由到本文件：开始审查 → 必读。

## 严重度三级

定级看后果，不看修复成本。同一项同时命中多级时取最高级。

| 级别 | 判定标准 | 处置 |
|------|----------|------|
| `blocker` | 会导致数据错误、安全问题或功能不可用 | 必须修完才能进入收尾，`spec-end` 不得放行 |
| `major` | 行为与已确认 plan 不符，或存在明确的失败路径未处理 | 应在本 Spec 内修 |
| `minor` | 可读性、命名、重复代码等 | 记录为延后项，不阻塞 |

判定要点：

- **数据错误**指落库或对外输出的值不正确，不是「日志不好看」。
- **功能不可用**指 plan 定义的路径走不通，不是「在极端输入下慢」。
- **「明确的失败路径未处理」**要能指出触发它的具体输入或状态，指不出就降级为 `minor`。
- 「我觉得这样写更好」不构成任何级别的发现项。改法偏好不是缺陷。

每个发现项必须写成「`file:line` + 现象 + 判定级别 + 依据」。给不出 `file:line` 的发现项不写进报告。

## 审查五类清单

逐类给出结论，不能跳类。某类无发现也要显式写「无」，附核对了哪些位置。

### ① 与已确认 plan 的一致性

- plan 定义的每个功能点、数据模型、接口签名，在代码中找到对应实现位置。
- 反向核对：代码里有没有 plan 之外的功能、字段、参数、配置项。
- 漏实现与超范围实现都是发现项，前者通常 `major` 或 `blocker`，后者按影响面定级。

### ② 错误与边界路径

- plan 或代码中每个可能失败的调用，失败分支是否被处理，还是被静默吞掉。
- 边界值：空集合、单元素、最大长度、零、负数、超时、并发重入。
- 只报能指出触发条件的路径。

### ③ 测试有效性

对 `executor/artifacts/` 覆盖的新增测试，套用 `../../spec-execute/references/tdd-discipline.md` 的门函数：

> **什么改动会让这个测试失败？**

答不出具体行为改动的测试，判为无效测试，级别按它所声称覆盖的功能定。同时对照该文件的「假测试的典型形态」：断言源文本、把实际输出粘成期望值、断言恒真。

注意边界：本类只判**测试是否可能因真实 bug 而失败**。完整的 Test Quality 评估不在此处做，见下文归属条款。

### ④ 证据一致性

- `executor/summary.html` 与 `tester/test-report.html` 的每条结论，在 `executor/artifacts/` 或 `tester/artifacts/` 里找到对应的实际输出。
- 核对命令、退出码、时间戳。报告说通过而证据里退出码非零，以证据为准，判 `blocker`。
- 报告引用了不存在的证据文件，或证据缺退出码/时间戳，判 `blocker`。
- 结论覆盖面大于证据覆盖面（报告声称验证了 5 个场景，证据只有 2 个），判 `major`。

### ⑤ 遗留物

- 调试代码：临时打印、断点、写死的测试数据、被临时放宽的断言。
- 注释掉的代码块。
- 本次改动新增的 `TODO` / `FIXME`，且没有对应的延后项记录。
- 临时文件、备份文件、误提交的本地配置。

## 限定复审

复审的范围只有两块：

1. 上一轮报告里的原始发现项——逐项核对是否真的修掉了。
2. 修复带来的 diff——只看这些行及其直接影响面。

**复审中发现的范围外新问题，一律记为延后次要项**，写进「问题闭环记录」，不在本轮扩大范围。例外只有一个：新问题本身是 `blocker`（数据错误/安全/功能不可用），此时按永远门禁处理，交回 TeamLead。

不设边界的复审会无限延长——每轮修复都产生新 diff，每轮新 diff 都能挑出新问题。

## 测试质量的归属

**Test Quality 评估归 `spec-tester`。** reviewer 不重做一遍。

| 判断 | owner |
|------|-------|
| executor 写的测试是否有效、覆盖是否够 | spec-tester |
| 最终测试结论 | spec-tester |
| tester 的结论是否被 `artifacts/` 里的实际输出支持 | spec-reviewer |

reviewer 的角色是核对证据链，不是当第二个测试评审员。两个 owner 判同一件事，结论冲突时没人负责。

reviewer 认为 tester 的测试质量结论本身有问题时，不直接改判，而是在「问题闭环记录」追加问题行，`owner` 写 `spec-tester`，附上支持这一质疑的证据位置。
