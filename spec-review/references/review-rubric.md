# 审查评级与清单

`spec-review` 运行契约的「参考」行路由到本文件：开始审查 → 必读。

## 审查立场

- **保持中立客观，优先指出方案与实现的缺陷与不足**，拒绝盲目附和与形式化夸赞；
- 审查着眼于风险防范、边界缺失与逻辑破损，以事实和可验证依据为准，不输出无依据的主观偏好。

## 对抗式审查与对称复验协议 (Adversarial Review Protocol)

时机对齐：在 `spec-execute`（代码实现完成）之后、`spec-end`（结项归档）之前介入。当引入独立视角（如外部高阶模型、专职红队审查者）进行对抗式评审时，审查方与修复方必须严格遵循以下闭环契约（参考 `spec/context/experience/exp-004-adversarial-review-rubric.md`）：

1. **审查方契约（实证定性）**：
   - 行为性缺陷（`blocker` / `major`）：严禁抽象空泛描述，必须给出「`file:line` + 触发条件 + 最小复现反例（Reproducer）」；
   - 静态非功能缺陷（`minor`）：可读性、冗余代码或排版格式等，维持「`file:line` + 现象 + 判定级别 + 具体规范依据」；
   - 缺陷按下方严重度标准明确评级，不得模糊定级。
2. **修复方契约（对称复验与机器状态终审）**：
   - **实测复现先行**：对行为性缺陷，收到意见后禁止直接修改代码，必须先在沙箱中运行反例确认缺陷真实存在并观察非零退出；
   - **对称反例复验**：完成修复后，必须使用当初捕获该漏洞的**同一套反例样本与控制流**再次实跑验证，证明其在修复后确凿通过（Exit: 0）；
   - **以真实机器状态为准**：严禁以文档中的文本标记替代底层状态，必须以真实工具输出（如 `awr doctor` 0 findings、`git status` clean、命令退出码 0）作为验收事实。

## 只读实测探针与 `[INFERENCE]` 标注规则

1. **只读实测边界**：`spec-reviewer` **不修改任何业务代码**（不修 bug、不改工作区）。对静态阅读存疑的行为性缺陷，允许在只读环境或临时沙箱目录（如通过 `git archive` 导出到系统临时目录，或运行不改变仓库状态的只读探针命令/脚本）构造最小反例并实跑验证，将真实命令与输出贴入审查报告。
2. **禁止空口定性**：凡标为 `blocker` 或 `major` 的行为性缺陷，必须附带可复核证据——要么引用 `executor/artifacts/`、`tester/artifacts/` 的既有实测输出，要么给出本次只读探针的命令与真实输出。
3. **`[INFERENCE]` 降级约束**：因环境受限、外部依赖不可用等客观原因确实无法实测的静态推断，必须在发现项描述与「复现依据 / 探针」列显式标注 `[INFERENCE]`。除显而易见的硬性契约缺失（如计划内接口未实现、必选元信息缺失）或明确高危安全漏洞外，纯 `[INFERENCE]` 不得直接定为阻断归档的 `blocker`。

## 多模型异构评审面板（可选，高风险 / `autopilot` 推荐）

- **适用场景**：`autopilot` 模式、高风险 `tech`/`debt` Spec、核心安全/资金/状态机改动，或存在设计争议的复杂变更。
- **编排方式**：借助 `.omp/agents/` 或角色配置预留的 `model` 字段，让 `spec-reviewer` 与 `spec-executor` 使用不同模型家族；必要时由 TeamLead 并行派生 2–3 个不同模型的只读审查视角交叉找茬。
- **合并硬纪律**：异构面板**不按多数票定案**；只将附带 `file:line` 与实测反例输出（或确定性契约缺口）的发现合并进 `reviewer/review.html`；未经实测证实的分歧统一标 `[INFERENCE]` 交由 TeamLead / 用户裁决。

## 严重度三级

定级看后果，不看修复成本。同一项同时命中多级时取最高级。

| 级别 | 判定标准 | 处置 |
|------|----------|------|
| `blocker` | 会导致数据错误、安全问题或功能不可用 | 必须修完才能进入收尾，`spec-end` 不得放行 |
| `major` | 行为与已确认 plan 不符，或存在明确的失败路径未处理 | 应在本 Spec 内修 |
| `minor` | 可读性、命名、重复代码等 | 记录为延后项，不阻塞 |

判定要点：

- **数据错误**指落库或对外输出的值不正确，不是「日志不好看」。
- **功能不可用**指 plan 定义的路径走不通，不是「在极端输入下慢」。
- **「明确的失败路径未处理」**要能指出触发它的具体输入或状态，指不出就降级为 `minor`。
- 「我觉得这样写更好」不构成任何级别的发现项。改法偏好不是缺陷。

每个发现项必须写成「`file:line` + 现象 + 判定级别 + 依据」。给不出 `file:line` 的发现项不写进报告。

## 审查五类清单

逐类给出结论，不能跳类。某类无发现也要显式写「无」，附核对了哪些位置。

### ① 与已确认 plan 的一致性

- plan 定义的每个功能点、数据模型、接口签名，在代码中找到对应实现位置。
- 反向核对：代码里有没有 plan 之外的功能、字段、参数、配置项。
- 漏实现与超范围实现都是发现项，前者通常 `major` 或 `blocker`，后者按影响面定级。

### ② 错误与边界路径

- plan 或代码中每个可能失败的调用，失败分支是否被处理，还是被静默吞掉。
- 边界值：空集合、单元素、最大长度、零、负数、超时、并发重入。
- 只报能指出触发条件的路径。

### ③ 测试有效性

对 `executor/artifacts/` 覆盖的新增测试，套用 `../../spec-execute/references/tdd-discipline.md` 的门函数：

> **什么改动会让这个测试失败？**

答不出具体行为改动的测试，判为无效测试，级别按它所声称覆盖的功能定。同时对照该文件的「假测试的典型形态」：断言源文本、把实际输出粘成期望值、断言恒真。

注意边界：本类只判**测试是否可能因真实 bug 而失败**。完整的 Test Quality 评估不在此处做，见下文归属条款。

### ④ 证据一致性与验证产物充分度

- `executor/summary.html` 与 `tester/test-report.html` 的每条结论，在 `executor/artifacts/` 或 `tester/artifacts/` 里找到对应的实际输出。
- 核对命令、退出码、时间戳。报告说通过而证据里退出码非零，以证据为准，判 `blocker`。
- 报告引用了不存在的证据文件，或证据缺退出码/时间戳，判 `blocker`。
- 结论覆盖面大于证据覆盖面（报告声称验证了 5 个场景，证据只有 2 个），判 `major`。
- **产物形态匹配度**：核对验证产物是否足以让人类审阅者不逐行读代码即判定行为正确（UI/交互改动须有关键截图/录屏及 console/network 摘要；状态流转改动须有异常/失败分支证据；后端/CLI 须有实跑命令与退出码输出）。UI/端侧变更仅有单测日志而缺失可视化产物（且未在 `tester/test-plan.html` 登记合理未验证风险）时，判 `major`。
- **用户路径与 `feature-map` 覆盖核对**：若项目存在 `spec/context/knowledge/feature-map.md`，对照本次变更涉及的用户入口，核查 `tester/artifacts/` 是否覆盖了关键用户路径，发现漏覆盖则记录为缺口并按影响面定级。

### ⑤ 遗留物与借口注释审查（白名单制）

- 调试代码：临时打印、断点、写死的测试数据、被临时放宽的断言。
- 注释掉的代码块。
- 本次改动新增的 `TODO` / `FIXME`，且没有对应的延后项记录。
- 临时文件、备份文件、误提交的本地配置。
- **注释白名单审查**：仅放行 5 类注释——① 法律/许可证头；② 公开 API 契约 docstring；③ 无法改造的外部依赖/平台/协议怪癖（须在实时路径上确有其事，而非己方代码设计缺陷）；④ Issue/RFC 链接（解释代码无法表达的外部/业务约束）；⑤ 纯风格格式化豁免（如 `prettier-ignore`）。
- **反「借口注释」与违规抑制**：为己方反模式/临时变通辩护的长段说明（如 `IMPORTANT` / `do not remove` / `fine for now` 却无外部白名单依据）以及屏蔽正确性/类型/安全规则的 `eslint-disable`、`@ts-ignore`、`@ts-expect-error`、`# type: ignore`，一律登记为发现项并指明需重命名/补类型/重构的具体符号（屏蔽正确性或安全规则定 `major`，其余冗余/辩护注释定 `minor`）。

### ⑥ 核心不变量与用户视角状态机（按需触发）

- **触发条件**：当 `writer/plan.html` 3.1 节列出了「核心不变量」，或本次 Spec 涉及多状态流转、异步重试与降级、并发重入、权限切换、复杂多态 UI 交互时必查；无状态流转的改动在对应章节写「不适用（本次无状态流转）」。
- **核查要点**：严格遵循 `references/statechart-review.md`，提炼用户视角不变量，从实际代码反向绘制 `figure.rk-fig` 内联 SVG 状态图，逐条给出违规/可疑状态的最短触发路径与代码证据（未实测须标 `[INFERENCE]`）。若执行了 TLA+/TLC 等形式化检查，必须对照真实代码回放反例；未回放证实前不得直接判为确凿 `blocker`。若项目启用了 `spec/context/ontology/ontology.json`，同步对照子图命中的 `INV`、`known_diff`、`experience_refs` 与高危边核对实现与测试是否真正落实（防“读过未落实”）。

## 限定复审

复审的范围只有两块：

1. 上一轮报告里的原始发现项——逐项核对是否真的修掉了。
2. 修复带来的 diff——只看这些行及其直接影响面。

**复审中发现的范围外新问题，一律记为延后次要项**，写进「问题闭环记录」，不在本轮扩大范围。例外只有一个：新问题本身是 `blocker`（数据错误/安全/功能不可用），此时按永远门禁处理，交回 TeamLead。

不设边界的复审会无限延长——每轮修复都产生新 diff，每轮新 diff 都能挑出新问题。

## 测试质量的归属

**Test Quality 评估归 `spec-tester`。** reviewer 不重做一遍。

| 判断 | owner |
|------|-------|
| executor 写的测试是否有效、覆盖是否够 | spec-tester |
| 最终测试结论 | spec-tester |
| tester 的结论是否被 `artifacts/` 里的实际输出支持 | spec-reviewer |

reviewer 的角色是核对证据链，不是当第二个测试评审员。两个 owner 判同一件事，结论冲突时没人负责。

reviewer 认为 tester 的测试质量结论本身有问题时，不直接改判，而是在「问题闭环记录」追加问题行，`owner` 写 `spec-tester`，附上支持这一质疑的证据位置。
